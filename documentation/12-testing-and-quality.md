# ۱۲ — تست و کیفیت

## ۱. وضعیت

| سنجه | مقدار |
|---|---|
| تست Backend | **۱۲۹** تست pytest — همه سبز |
| تست Frontend | **۱۲** تست Karma/Jasmine — همه سبز |
| لینت Backend | `ruff` — بدون خطا |
| زمان اجرای مجموعه‌ی Backend | چند ثانیه (SQLite درون‌فایلی، بدون سرویس خارجی) |
| پوشش‌دهی | `pytest-cov` نصب است؛ گزارش پوشش بخشی از خط لوله نشده |

```bash
cd backend && python -m pytest && python -m ruff check .
cd Rorschach && npx ng test --watch=false --browsers=ChromeHeadless
```

## ۲. فلسفه‌ی تست

سه قاعده در سراسر مجموعه رعایت شده است:

1. **تست از راه HTTP، نه از راه سرویس.** تقریباً همه‌ی تست‌ها با `APIClient` کار
   می‌کنند. دلیلش این است که آنچه باید محافظت شود **قرارداد** است: اگر یک فیلد
   حذف شود یا کد وضعیت عوض شود، تست باید بشکند — حتی اگر منطق درونی درست باشد.
2. **هر قاعده‌ی کسب‌وکار دست‌کم یک تست دارد.** نگاشت کامل در [[13-traceability]].
3. **تست‌ها بدون سرویس خارجی اجرا می‌شوند.** SQLite، cache درون‌حافظه‌ای، لایه‌ی
   کانال درون‌حافظه‌ای و Celery همزمان. همان مجموعه با تنظیم `DATABASE_URL` روی
   PostgreSQL هم اجرا می‌شود.

پیکربندی تست در `config/settings/testing.py` عمداً پارامتر `--ds` را در
`pyproject.toml` اجباری می‌کند، چون `pytest-django` اجازه می‌دهد یک
`DJANGO_SETTINGS_MODULE` محیطی بر فایل پیکربندی غلبه کند — و کانتینرها
`config.settings.development` را export می‌کنند. بدون آن، `docker compose exec backend
pytest` روی Redis و کارگزار واقعی اجرا می‌شد و تست‌های وابسته به Celery همزمان
می‌شکستند.

## ۳. Fixtureها

در `backend/conftest.py`:

| Fixture | کار |
|---|---|
| `api` | یک `APIClient` بدون احراز هویت |
| `as_user` | کلاینتی که با توکن کاربر داده‌شده احراز هویت شده |
| `make_patient` · `make_psychologist` · `make_admin` | ساخت کاربر با پروفایل |
| `patient` · `psychologist` | نمونه‌های آماده |
| `link` | رابطه با وضعیت دلخواه |
| `rorschach` | یک نسخه‌ی منتشرشده‌ی ده‌کارتی — **همان شکلی که `seed_catalog` می‌سازد** |

اینکه `rorschach` دقیقاً ساختار واقعی را بسازد اهمیت دارد: تست موتور آزمون روی همان
ساختاری اجرا می‌شود که در production وجود دارد، نه یک ساختار ساده‌شده.

## ۵. تست موتور آزمون

فایل `test_engine.py` با ۳۰ تست، ستون فقرات مجموعه است. پوشش آن:

| گروه | تست‌ها |
|---|---|
| ایجاد جلسه | نیاز به رابطه‌ی فعال · ایجاد دوباره همان جلسه‌ی باز را می‌دهد · ثبت نسخه‌ی اجراشده |
| شروع | انتقال به کارت اول · idempotent بودن |
| ثبت پاسخ | متن خالی رد می‌شود · ارسال تکراری یک رکورد می‌سازد · پاسخ ثبت‌شده فقط‌خواندنی است · کارت کهنه `409` می‌دهد · بدون سقف پاسخ · انباشت چرخش کارت |
| کارت بعد | بدون پاسخ رد می‌شود · یک پاسخ ← یک یادآوری سپس پیشروی · کارت دهم ← مرحله‌ی روشن‌سازی |
| روشن‌سازی | نیاز به دلیل یا توضیح · نیاز به محل (مگر «کل تصویر») · حذف دلایل ناشناخته و تکراری · idempotent · دست نزدن به متن اصلی |
| تکمیل | پیش از مرحله‌ی مرور `409` · یک تحلیل می‌سازد · تکرارش بی‌اثر است · پس از تکمیل، اندپوینت‌های اجرا بسته می‌شوند |
| بازیابی | وضعیت پس از بارگذاری دوباره همان است · وقفه ثبت می‌شود |
| مجوز | مراجع دیگر `403` · روان‌شناس نامرتبط `403` · روان‌شناس نمی‌تواند اجرا کند · جلسه‌ی ناشناخته `404` · ناشناس `401` |

نکته‌ی فنی: تست‌های تکمیل از `django_capture_on_commit_callbacks` استفاده می‌کنند تا
کاری که با `transaction.on_commit` زمان‌بندی شده واقعاً اجرا شود — وگرنه در محیط تست
که همه‌چیز در یک تراکنش rollback می‌شود، هرگز اجرا نمی‌شد.

## ۶. تست محاسبات R-PAS

`test_scoring.py` تنها فایلی است که مستقیم روی تابع محاسبه کار می‌کند، چون ریاضیات را
بدون واسطه‌ی HTTP می‌سنجد:

| تست | ادعا |
|---|---|
| بدون کدگذاری | فقط متغیرهای اجرایی محاسبه می‌شوند؛ بقیه `null` می‌مانند |
| وزن‌دهی رنگ | `WSumC` و `MC` طبق فرمول |
| کیفیت فرم | `FQ-%` فقط روی پاسخ‌های دارای کیفیت فرم قابل ارزیابی |
| فرم خالص | فقط پاسخ‌هایی که **تنها** عاملشان `F` است |
| کدهای شناختی | وزن‌دهی `WSumCog` و شمارش `SevCog` |
| توازن منابع | `PPD` و `MC − PPD` |
| زمان واکنش | میانگین، با نادیده گرفتن اندازه‌گیری‌های خالی |
| پروتکل کوتاه | یافته‌ی «کمتر از بازه‌ی توصیه‌شده» |
| هشدارها | هر خروجی همیشه هر دو هشدار اجباری را دارد (BR-18) |
| کدگذاری ناقص | هشدار «شاخص‌ها موقت‌اند» |

## ۷. تست مسیر بحرانی

`test_critical_path.py` یک تست است که کل چرخه را می‌رود و **فقط از راه HTTP**:

```
ثبت‌نام مراجع و روان‌شناس → بارگذاری مدارک → تأیید ادمین → ورود
→ درخواست ارتباط → تأیید روان‌شناس → ایجاد و شروع آزمون
→ پاسخ به ۱۰ کارت (با رعایت قاعده‌ی یادآوری) → روشن‌سازی هر پاسخ
→ ثبت نهایی → ورود روان‌شناس → مشاهده‌ی پروتکل → کدگذاری → تحلیل
```

ارزش این تست در این است که **هیچ‌جا میان‌بر نمی‌زند**: اگر یک اندپوینت حذف شود، یک
فیلد تغییر نام دهد یا یک مجوز سخت‌گیرتر شود، همین تست می‌شکند.

## ۹. آنچه تست نشده است

صادقانه، این‌ها پوشش ندارند:

| مورد | چرا / چه باید کرد |
|---|---|
| **WebSocket** | مصرف‌کننده دستی در مرورگر تأیید شده ولی تست خودکار ندارد؛ نیازمند `pytest-asyncio` و `ChannelsLiveServer` |
| **کامپوننت‌های Angular** | تست‌های فرانت‌اند روی سرویس و منطق‌اند، نه روی رندر صفحات |
| **مسیر end-to-end در مرورگر** | ابزار e2e (مثل Playwright) راه‌اندازی نشده؛ مسیر بحرانی در سطح HTTP پوشش دارد |
| **بارگذاری واقعی به Object Storage** | تست‌ها از `InMemoryStorage` استفاده می‌کنند |
| **محدودسازی نرخ** | در محیط تست خاموش است تا نتیجه‌ها قطعی بمانند؛ منطق fail-open تست جداگانه ندارد |
| **مهاجرت‌های دیتابیس روی PostgreSQL در CI** | به‌صورت محلی اجرا شده، در خط لوله‌ی خودکار نه |
| **شکاف D-13** | رفتار روان‌شناس تعلیق‌شده تست ندارد، چون هنوز رفتار مطلوبی برایش تعریف نشده |

## ۱۰. کیفیت کد

`ruff` با ۹ گروه قاعده روی کل مخزن (به‌جز مهاجرت‌ها و محیط مجازی):

```
E (pycodestyle) · F (pyflakes) · W · I (isort) · UP (pyupgrade)
B (bugbear) · C4 (comprehensions) · DJ (Django) · RUF
```

پنج قاعده عمداً خاموش‌اند و دلیل هرکدام در `pyproject.toml` نوشته شده:

| قاعده | چرا خاموش |
|---|---|
| `RUF001` · `RUF002` · `RUF003` | متن فارسی همه‌جا «کاراکتر یونیکد مبهم» تشخیص داده می‌شود |
| `RUF012` | صفت‌های کلاس در Django ذاتاً تغییرپذیرند |
| `B008` | الگوی رایج Django/DRF |
| `DJ001` | قرارداد API روی فیلدهای متنی اختیاری، `null` را از `""` تفکیک می‌کند |

علاوه بر لینت، سه عادت در کد رعایت شده که ابزار نمی‌سنجد اما در بازبینی دیده می‌شود:

- هر توضیح کد می‌گوید **چرا**، نه **چه**.
- هر تصمیم غیرشهودی (مثل fail-open بودن محدودکننده‌ی نرخ یا نسبی ماندن `image_url`)
  دقیقاً کنار خودش توضیح دارد.
- هیچ فایل خالی یا کلاس بی‌استفاده ساخته نشده — با یک استثنای شناخته‌شده که در
  D-13 ثبت شده است.

## ۱۱. اجرای مجموعه‌ی تست روی PostgreSQL

پیش‌فرض SQLite است تا اجرا سریع و بدون سرویس باشد، اما هدف واقعی PostgreSQL است.
برای اطمینان از سازگاری:

```bash
DATABASE_URL=postgres://rorschach:rorschach@localhost:5432/rorschach_test python -m pytest
```

مدل‌ها عمداً فقط از نوع‌های قابل‌حمل استفاده می‌کنند (`JSONField` و نه `ArrayField`
مخصوص PostgreSQL)، پس همین یک دستور کافی است.
